Technical plan · Entity resolution

Merging duplicate companies into one record

A re-runnable Python script that reads a company CSV, decides which rows describe the same real-world business, consolidates them into a single golden record — and publishes a complete audit trail of every merge it made, shaped for a Tableau dashboard.

Input company name + address Scale 50k–500k rows Method weighted fuzzy rules Decision automatic, fully audited

01

The problem

The same company shows up in the file many times over. It arrives with a different legal suffix, a shortened trading name, a typo, an abbreviated street, a postcode with or without a space. Nothing in the data says these rows belong together, so every downstream count is inflated: one customer is counted as five, revenue is split across phantom accounts, and territory coverage looks broader than it is.

The fix is entity resolution — deciding which records refer to the same real-world entity, then collapsing each group into one consolidated record while keeping a traceable link from every original row to the record that replaced it.

Two constraints shape the whole design. First, the only signals available are the company name and its address. There is no web domain, no company registration number, no tax ID — the near-deterministic keys that make this problem easy are simply not in the file, so name and address similarity have to carry all of the weight. Second, at 500,000 rows the naive approach is not merely slow, it is arithmetically impossible.

02

Shape of the solution

A standalone Python package, run from the command line against a CSV. It never modifies the input file — it writes a new set of tables alongside it. Every threshold, weight and column mapping lives in a YAML config, so tuning the matcher never requires touching code.

company-match/
  config/config.yaml          column mapping, weights, thresholds
  src/company_match/
    cli.py                  entrypoint
    io.py                   load CSV, map columns, write outputs
    normalize.py            name + address standardisation
    blocking.py             candidate pair generation
    features.py             pairwise similarity features
    scoring.py              weights, hard rules, decision bands
    cluster.py              Union-Find + cohesion guardrail
    survivorship.py         build the golden record
    report.py               Tableau outputs + run metrics
  tests/                   pytest
  data/sample/             synthetic CSV with known duplicates
  tableau/DASHBOARD_GUIDE.md

Run it with a single command:

python -m company_match.cli \
    --input companies.csv \
    --config config/config.yaml \
    --outdir ./out

Dependencies

pandas, rapidfuzz (fast string similarity), scikit-learn and scipy (sparse TF-IDF neighbours), jellyfish (phonetic keys), pyyaml, pytest. Optionally pantab to write a Tableau .hyper extract directly.

Deliberate omission

libpostal is the best address parser available and it is being left out on purpose — it needs a large C build and a multi-gigabyte model, which makes the tool hard to install and hard to run anywhere else. Rule-based address normalisation covers the common cases; libpostal stays documented as an upgrade if address quality proves to be the binding constraint.

03

The pipeline

Eight stages, run in order. Each writes its intermediate state so a failed or surprising run can be inspected at the point it went wrong rather than re-run blind.

  1. 01

    Ingest & profile

    Load every column as text — letting the parser guess types silently destroys postal codes by stripping leading zeros and reformatting them as numbers. Assign each row a stable record_id so results are comparable across runs.

    Emit a profile first: row count, null rate per field, exact-duplicate count. If a critical field is 60% empty, that needs to be known before interpreting any match rate.

  2. 02

    Normalisation

    The highest-leverage stage in the pipeline. Most apparent differences between duplicate records are formatting, not substance, and normalisation removes them before any comparison happens.

    Names produce two forms, both kept:

    • name_norm — lowercased, accents folded to ASCII, punctuation stripped, whitespace collapsed, & expanded to and.
    • name_core — name_norm with legal suffixes removed: inc, llc, ltd, limited, plc, gmbh, sa, srl, bv, pty, corp, holdings, group.

    Keeping both matters. Acme Ltd and Acme Inc share a name_core but are frequently distinct legal entities — so suffix agreement becomes its own scored feature rather than information that was quietly thrown away.

    Also derived: a token set, a sorted-token key, a phonetic key (Double Metaphone of the first significant token), and the initials of multi-word names, so IBM against International Business Machines is at least detectable — flagged for attention, never merged on that signal alone.

    Addresses get street types canonicalised (street→st, avenue→ave), suite and unit numbers split into their own field, postal codes uppercased and trimmed to a comparable prefix, and states and countries mapped to ISO codes.

  3. 03

    Blocking

    Generate candidate pairs cheaply so expensive scoring only runs where a match is plausible. Four keys are used and their results unioned, so a defect that breaks one key is caught by another:

    • Postal prefix + first four characters of the name — the workhorse.
    • Country + city + first sorted name token — survives a wrong or missing postcode.
    • Phonetic key + state — catches names that sound alike but are spelt differently.
    • TF-IDF character-trigram nearest neighbours within country — catches typos that defeat every literal key, because a trigram profile degrades gracefully where a prefix match fails outright.

    A size cap prevents blocks built on generic values from exploding back into a quadratic comparison. Every capped block is logged, so recall lost to the cap is visible rather than silent.

  4. 04

    Pairwise scoring

    Nine similarity features per candidate pair, combined into a single weighted score, with a set of hard rules that can veto a match regardless of how high that score is. Detailed in section 04.

  5. 05

    Clustering

    Accepted pairs are merged into groups with Union-Find. This is where a subtle failure lives: matching is pairwise but grouping is transitive, so if A matches B and B matches C, A and C land in the same company even if they look nothing alike. Long chains of near-misses drift into a single bloated cluster.

    The guardrail is a cohesion check. After grouping, recompute the weakest pairwise score inside each cluster; where it falls below a floor, the cluster is re-split at a stricter threshold. Cluster IDs are derived from a hash of their sorted members, so they stay stable across runs.

  6. 06

    Survivorship

    Build the one consolidated record that represents the cluster. Configurable field-level rules: the surviving name is the most frequent spelling among members, tie-broken by completeness; address fields are taken from the most complete member.

    Every surviving field records which record it came from, so the golden record is fully traceable back to source rather than being a black box.

  7. 07

    Publish for Tableau

    Four flat, joinable tables written as CSV, each stamped with a run_id. Detailed in section 05.

  8. 08

    Evaluate

    A separate mode that scores the matcher against hand-labelled pairs and reports precision and recall across candidate thresholds. Detailed in section 06.

04

Scoring model

Each candidate pair is scored on nine features. These are starting weights, intended to be tuned against labelled data in phase five rather than trusted as-is.

FeatureWhat it measuresWeight
name_token_setToken-set ratio on the core name — tolerant of word order and extra words0.30
name_tfidf_cosCharacter-trigram cosine — tolerant of typos0.15
postal_matchExact postcode, scored lower for prefix-only agreement0.15
name_jaro_winklerEdit-distance similarity, weighted toward matching prefixes0.10
street_simSimilarity on the normalised street name0.10
house_numberExact match on building number0.08
legal_suffixAgreement, one-side-missing, or outright conflict0.05
city_matchExact or fuzzy city agreement0.05
state_matchExact state or region agreement0.02
Total1.00
The detail that decides whether this works

Missing fields renormalise the weights rather than score zero. If two records have no postcode, the pair is judged on the features that are present, not penalised for an absence neither record could help. Scoring a missing field as a mismatch is the single most common reason a matcher rejects everything on sparse data — every pair drifts below threshold for reasons unrelated to whether it is a match.

Hard rules that override the score

Some differences are disqualifying no matter how similar two records look. These are checked independently of the weighted score and can veto a merge outright.

  • Conflicting countries never merge. Two records with different, populated country codes are different entities, whatever their names say.
  • Conflicting numeric tokens never merge. Store 41 and Store 47 score above 0.95 on every string metric and are obviously different locations. This is the most common source of false merges, and no amount of threshold tuning fixes it — only an explicit rule does.
  • Junk names are excluded. unknown, n/a, test, none and similar placeholders are dropped from matching entirely, or they collapse into one enormous meaningless cluster.

Decision bands

The script decides — nothing waits on a person. But the decision is banded rather than a single cutoff, so that merges made near the boundary are visibly distinguished from confident ones in the dashboard.

≥ 0.92
auto merge

Merged. Strong agreement on both name and address; these need no attention.

0.80 – 0.92
merge · low confidence

Merged, and flagged. Real but imperfect agreement — surfaced prominently in Tableau for spot-checking.

< 0.80
no merge

Kept separate. Still written to the pairs table so near-misses can be reviewed and thresholds tuned.

Every pair carries a plain-language reason alongside its score — name 0.97, postal exact, city exact — so a merge can be explained on the dashboard without reading any code.

05

Outputs for Tableau

Four flat tables, joinable in Tableau with no data prep. The crosswalk is the hub: it is what allows a dashboard to move between an original row and the consolidated company that replaced it, in either direction.

TableGrainWhat it carries
golden_companies 1 per cluster Consolidated name and address, member count, cluster confidence, and per-field provenance showing which source record each surviving value came from
crosswalk 1 per input record record_id, cluster_id, survivor flag, similarity to the golden record
match_pairs 1 per scored pair Both record IDs, all nine feature scores, total score, decision band, and the plain-language reason
run_metrics 1 per run Counts per decision band, cluster size distribution, duplication rate, runtime, config hash

Dashboard specification

A companion guide ships with the outputs, specifying the sheets to build:

  • Headline figures — input rows against golden companies, percentage reduction, and the split between confident and low-confidence merges.
  • Cluster size distribution — a histogram whose long tail is the first place over-merging shows up. A cluster of 400 records is a bug, and it is visible at a glance.
  • Score distribution with the two thresholds drawn as reference lines, so the cost of moving a threshold is visible before anyone moves it.
  • Merge audit — the sheet that answers "what did it merge?". Pick a company, see its source records side by side with differing fields highlighted and the pair scores that joined them.
  • Geographic view — duplication rate by country and region, which usually exposes one badly-formatted source system.

Because every table carries a run_id, successive runs can be compared on the same dashboard — making the effect of a threshold change measurable rather than a matter of opinion.

06

Proving it works

A matcher that has not been measured is a guess. The weights and thresholds above are a considered starting point, not a result, and the only way to know whether 0.92 is the right cutoff is to test it against pairs whose correct answer is known.

The method is to hand-label roughly 300 pairs, sampled deliberately across the score range rather than at random — random sampling from 5 million pairs returns almost nothing but obvious non-matches. Oversampling the 0.70–0.95 region concentrates the labelling effort exactly where the threshold decision is actually made.

The script then runs in evaluation mode against those labels and reports precision, recall and F1 at every candidate threshold. That turns threshold-setting into an explicit trade: this cutoff buys that much precision at that much recall. The same labelled set becomes a regression suite, so a future tuning change that quietly breaks matching is caught rather than shipped.

Alongside this, unit tests cover every normalisation rule, and a small synthetic file with known duplicates runs end-to-end in CI, asserting that the expected clusters form.

07

Machine learning path

Machine learning is deferred to phase two, and deliberately so — a supervised model needs labelled examples, and those do not exist yet. Building the rules-based matcher first is what produces them.

The match_pairs table is already a feature matrix: one row per pair, nine numeric features, plus a decision. Attaching labels to it makes it a training set with no extra engineering work. The upgrade path from there:

  • Logistic regression — learned coefficients replace hand-tuned weights. Still fully interpretable, and directly comparable to the weights table above, which makes it easy to see what the data disagrees with.
  • Gradient boosting (LightGBM) — captures interactions the linear model cannot, such as name similarity mattering far more when the postcode is missing.
  • Splink — a probabilistic Fellegi-Sunter matcher that learns its weights unsupervised, via expectation-maximisation. Worth evaluating first, because it needs no labels at all and would sidestep the labelling effort entirely.

In every case the model outputs a calibrated probability that replaces the weighted score. The band logic, the hard rules, the clustering and all four output tables stay exactly as they are — the model swaps into one slot rather than requiring a rebuild.

09

Limits & risks

Name and address alone impose a ceiling

With no domain, registration number or tax ID, roughly 95–98% precision is the realistic target — not 100%. Two cases are genuinely hard and no amount of tuning fully resolves them: franchises and chains, which share a name across many real addresses and should stay separate; and subsidiaries registered at a shared head office, which share an address while being distinct entities. If a domain or registration number can be sourced for even part of the file, it would raise the ceiling more than any modelling improvement discussed here.

Automatic merging is destructive when it is wrong

Three things contain this. The input file is never modified. The crosswalk retains every original record ID, so any merge can be undone from the outputs. And low-confidence merges are separated into their own band rather than blended in with confident ones, so the riskiest decisions are the easiest ones to find on the dashboard.

Blocking can silently lose true matches

Any pair the blocking stage never generates cannot be matched, however similar it is. Four overlapping keys make this unlikely, and capped blocks are logged rather than dropped quietly — but recall lost at this stage is invisible in the final numbers, which is exactly why the evaluation set in phase five measures recall and not just precision.
